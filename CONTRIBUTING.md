# Contributing to kalku

kalku measures whether a test suite notices a defect. That makes one
thing load-bearing: **a result has to be true**. A survivor that is not
real, or a kill that is not earned, is worse than no measurement, because
someone will act on it. Most of what follows comes from that.

The principles are in [`CLAUDE.md`](CLAUDE.md), and the topic rules in
[`.claude/rules/`](.claude/rules/). They are written for whoever works
here, human or agent.

## Before you start

- **Open an issue first** for anything beyond a fix, so the design gets
  argued before the code exists.
- **One pull request does one thing.** A bug you find outside its scope
  becomes an issue, not an extra commit.
- Pending work lives in GitHub issues, not in tracking documents.

## Building and testing

You need [kaikai](https://kaikai-lang.org/) at the version in
`.kaikai-version`, plus [`km`](https://github.com/lnds/kimun) and `jq`
for the quality gate. Elixir 1.16 and OTP 26, or newer, for the Elixir kalku.

```sh
make build         # the binary
make ci            # what CI runs on the kaikai side
make check         # that, plus the Elixir kalku's tests
make self-mutate   # kalku on its own sources, through its own kalku
```

`make ci` has to pass, and it includes `km`: every file scores **A− or
better, B is the hard floor**, under 400 lines, no new duplicate groups.
A high complexity number is a design smell, not a threshold to argue
with.

## What a change is expected to bring

- **Every fix brings a fixture that reproduces the bug.** Not a test
  that would have caught it in principle — the actual case, so it cannot
  come back quietly.
- **Tests before properties.** A `test` for the case at hand, more for
  the edges, and a `check` once several tests are visibly the same
  invariant with different data. A property written before the invariant
  is understood passes by accident.
- **Measure before claiming speed.** A performance claim comes with
  numbers from a real project.

## Language and words

Code, comments, commit messages, pull requests and documentation are in
**English**, whatever language the conversation happened in.

Use the glossary consistently — **kalku**, **wekufe**, **spell**,
**site**, **reni**, **summon**, **banish**, **cast** — and do not mix in
synonyms where a glossary word exists. Outcomes keep plain technical
names (`killed`, `survived`, `timeout`, …) because they appear in CI logs
and have to read without the glossary.

Comments are brief and timeless: they explain what the code does and why,
not which issue prompted it. The why that depends on context belongs in
the commit message or the pull request.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/), with the
area as the scope: `feat(elixir): add arm spell`, `fix(scheduler): …`,
`feat(protocol)!: …` with a `BREAKING CHANGE:` footer.

`feat` → "Added" and a MINOR bump; `fix` → "Fixed", PATCH;
`perf`/`refactor` → "Changed", PATCH; `docs`, `chore`, `ci`, `test` and
`build` change no version and add no changelog entry.

Do not edit `CHANGELOG.md` or `VERSION` by hand. They are generated at
release time from the commit messages.

## Things this project does not do

- **No workarounds for gaps in kaikai.** If the kaikai side needs
  something the compiler or `kai test` does not give, the fix is an issue
  on kaikai, not a detour here.
- **No parser for a target language written in kaikai.** Sites come from
  the target's own parser, through its kalku.
- **No scanning source text for sites.** A regex that mutates a string
  literal produces noise, not a measurement.
- **No casting spells on test code.** Mutating the oracle measures
  nothing about the oracle.
- **No hints generated by a model.** Survivor hints are fixed templates
  per spell, filled from the site.
